## AI-generated contributions policy

### This project is built by humans, for humans. We only accept real, human-written open source contributions.

### Pull requests, issues and comments that are generated by AI tools (for example ChatGPT, Claude, Copilot agents, Cursor or similar) will be closed without review.

This applies to:
- Code, tests and documentation produced mostly or entirely by an AI tool.
- Pull requests opened by autonomous agents or bots (other than the project's own CI and dependency tooling).
- Bug reports, feature requests or review comments written by an AI and pasted in without being verified by a person.

Why we have this rule:

- Reviewing code costs maintainers real time, and unverified generated code often looks correct but is subtly wrong.
- We want contributors who understand the code they submit, can explain their decisions and can respond to review feedback.
- It keeps the project's code and licensing clear: you must be the author of what you submit.

What is still fine:

- Using your editor's regular tooling, such as autocomplete of single identifiers, spell checking or formatting.
- Using a translator to help you write in English.

## Code of conduct

Be respectful and constructive. Assume good intent, welcome newcomers, and keep feedback focused on the code and the idea, not the person. Harassment or discrimination of any kind is not tolerated. Maintainers may edit, close or remove contributions that don't follow these rules.

## Ways to contribute

You don't have to write code to help:

- Report a bug or a confusing behavior.
- Suggest an improvement or a new feature.
- Improve the README, dartdoc comments or the example app.
- Answer questions from other users in issues and discussions.
- Add or improve tests.
- Review open pull requests.

## Reporting bugs

Before opening an issue:

1. Search the existing issues (open and closed) to avoid duplicates.
2. Update to the latest version of the package and check whether the problem is already fixed.
3. Run `flutter doctor -v` and make sure your setup is healthy.

When you open a bug report, please include:

- A clear title and a short description of the problem.
- The expected behavior and the actual behavior.
- A minimal code sample or a small repository that reproduces the issue. This is the single most helpful thing you can provide.
- The package version, Flutter version, Dart version and target platform (Android, iOS, web, desktop).
- Logs, stack traces or screenshots when relevant.

## Suggesting features

Open an issue describing:

- The problem you are trying to solve (the use case, not only the solution).
- Your proposed API or behavior, with a small code example of how you would like to use it.
- Alternatives you considered.

## Development setup

1. **Fork** the repository and clone your fork:

   ```bash
   git clone https://github.com/koukibadr/Searchable-Listview.git
   cd Searchable-Listview
   ```

2. **Install Flutter** using a version that satisfies the constraints in `pubspec.yaml`. Contributions are checked against the minimum supported version and the latest stable release, so testing on both is ideal.

3. **Install the dependencies:**

   ```bash
   flutter pub get
   cd example && flutter pub get && cd ..
   ```

4. **Verify everything works** before you change anything:

   ```bash
   flutter analyze
   flutter test
   ```

## Project structure

```
lib/           Package source code (public API is exported from lib/searchable_listview.dart)
test/          Unit and widget tests
example/       Example app demonstrating the package
CHANGELOG.md   Release notes
```

Anything under `lib/src` (or files not exported from the main library file) is considered internal and may change without notice.

## Making changes

1. Create a branch from the latest `main`. Use a descriptive name:

   ```bash
   git checkout -b fix/brief-of-the-issue/empty-widget-flicker
   git checkout -b feat/brief-of-the-issue/search-controller
   ```

2. Keep each pull request focused on **one** change. Several small pull requests are easier to review and merge than one large one.

3. Make your changes and add or update tests, documentation and the example app when relevant.

4. Run the checks locally (see [Testing](#testing) and [Code style](#code-style)).

5. Push your branch and open a pull request against `main`.

## Code style

- Follow the [Effective Dart](https://dart.dev/effective-dart) guidelines.
- Format all code with `dart format .` before committing.
- The code must pass `flutter analyze` with no errors, warnings or lints.
- Prefer clear names over comments, and keep functions small.
- Keep the public API small and consistent. New parameters should be optional and have sensible defaults so that existing users are not affected.
- Avoid adding new dependencies. If one is truly needed, explain why in the pull request.
- Don't use language or Flutter APIs newer than the minimum versions declared in `pubspec.yaml`.

## Testing

Every bug fix and feature should come with tests.

```bash
flutter test                 # run all tests
flutter test --coverage      # with coverage
flutter test test/some_test.dart   # a single file
```

Guidelines:

- A bug fix should include a test that fails before the fix and passes after it.
- Cover the different constructors and modes of the widget when your change touches shared behavior.
- Test edge cases: empty lists, empty queries, rapid typing, widget disposal during async work, and rebuilds with new parameters.
- Don't depend on real network calls or real time. Use fakes and `tester.pump` with explicit durations.

## Documentation

- Add dartdoc (`///`) comments to every public class, method and parameter. Explain what it does, its default value and any caveats.
- Update the README when you add or change user-facing behavior.
- Add a usage example to the `example/` app for any significant new feature.
- Add an entry to `CHANGELOG.md` under an "Unreleased" heading describing the change.

## Commit messages

Write short, meaningful commit messages in the imperative mood. We recommend the [Conventional Commits](https://www.conventionalcommits.org/) format:

```
feat: add controller to filter the list programmatically
fix: keep cursor position when clearing the search field
docs: clarify the asyncDebounceTime parameter
test: cover expansion list filtering
refactor: extract list rendering into a separate widget
chore: update CI workflow
```

Reference related issues in the pull request description (for example, `Closes #123`).

## Pull request checklist

Before you request a review, please check that:

- [ ] The pull request has a clear title and describes **what** changed and **why**.
- [ ] It is linked to an issue when one exists.
- [ ] `dart format .` has been run.
- [ ] `flutter analyze` reports no issues.
- [ ] `flutter test` passes.
- [ ] New or changed behavior is covered by tests.
- [ ] Public APIs have dartdoc comments.
- [ ] The README and example app are updated when needed.
- [ ] `CHANGELOG.md` has an entry.
- [ ] The change does not break existing users, or the breaking change is clearly called out.

A maintainer will review your pull request as soon as possible. Please be patient, and respond to feedback so the review can move forward. Pull requests that stay inactive for a long time may be closed, and you are always welcome to reopen them.

## Versioning and breaking changes

This package follows [Semantic Versioning](https://semver.org/):

- **Patch** (`x.y.Z`): backwards-compatible bug fixes.
- **Minor** (`x.Y.0`): backwards-compatible new features and deprecations.
- **Major** (`X.0.0`): breaking changes.

Breaking changes are only released in major versions. When you need to replace or remove public API, first deprecate it with `@Deprecated('Use X instead.')` in a minor release so that users get a warning period, and add a note to the migration guide.

## Release process (maintainers)

1. Make sure `main` is green (analysis and tests pass on the minimum supported and latest stable Flutter).
2. Update the version in `pubspec.yaml`.
3. Move the "Unreleased" entries in `CHANGELOG.md` under the new version and date.
4. Run a dry run and fix any warnings:

   ```bash
   dart pub publish --dry-run
   ```

5. Tag the release and publish:

   ```bash
   git tag vX.Y.Z
   git push origin vX.Y.Z
   dart pub publish
   ```

6. Create a GitHub release with the changelog notes.
